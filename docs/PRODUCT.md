# Teyvat Tasks: описание продукта

## Цель и ограничения

Неофициальный русскоязычный веб-менеджер задач для Genshin Impact для игрока, который вручную отмечает прогресс и планирует занятия. Интерфейс должен быть понятен начинающему пользователю.

Технологии: HTML, CSS, JavaScript с ES Modules, `localStorage`, встроенный Node.js test runner. Без React, серверной части и платных API. Логины, пароли и токены HoYoverse не запрашиваются. Интеграции, облачная синхронизация и публикация не входят в начальный этап и требуют отдельного подтверждения.

## Семь экранов

| Экран | Назначение |
| --- | --- |
| Обзор | Сводка активного профиля: задачи, цели и расчёт смолы |
| Рутина | Повторяющиеся задачи и отметки выполнения за игровой период |
| Персонажи | Вручную введённые персонажи и планы их развития |
| Фарм | Цели по материалам и планы фарма |
| Мои цели | Личные задачи и цели игрока |
| Статистика | Сводки на основе сохранённых отметок выполнения |
| Настройки | Профили, параметры игрового сервера и приложения |

Реализованы оболочка с двумя темами, рутина, приблизительный трекер смолы, ручные персонажи с материалами и планы фарма. На «Обзоре» отображается готовность материалов. Также реализованы личные задачи с фильтрами и статистика по первичным записям.

## Единое хранилище

Ключ `localStorage`: `teyvat-tasks:v1`. Значение — один JSON-документ с явной версией схемы `schemaVersion: 1` и следующими коллекциями:

| Коллекция | Данные |
| --- | --- |
| profiles | Игровые профили и выбор сервера |
| settings | Настройки приложения и профилей |
| taskTemplates | Шаблоны повторяющихся задач |
| completions | История выполнения задач с привязкой к игровому периоду |
| personalTasks | Личные задачи |
| characters | Персонажи и введённый прогресс |
| materialGoals | Цели накопления материалов |
| farmPlans | Планы фарма |
| resinSnapshots | Последовательные записи ручных замеров и расхода смолы с временем UTC |

Коллекция `settings` — объект с полями `theme` (`light` или `dark`) и `lastPage` (`overview`, `routine`, `characters`, `farm`, `goals`, `statistics`, `settings`). Остальные восемь коллекций — массивы, изначально пустые. По умолчанию выбраны светлая тема и обзор.

Состав игровых полей записей будет определяться вместе с соответствующей логикой. Текущая валидация проверяет версию, настройки, наличие массивов, непустые уникальные строковые `id` внутри каждого массива и ссылки `profileId` на существующий профиль для всех записей, кроме самих профилей. Неизвестные дополнительные поля сохраняются; автоматических миграций пока нет. Для шаблонов и истории действуют дополнительные проверки, описанные ниже. Записи должны иметь устойчивые идентификаторы; данные профиля — ссылку на его идентификатор. Завершения нужно хранить отдельно от шаблонов, чтобы сохранять историю.

Чтение, проверка структуры, сериализация и миграции принадлежат модулю хранения. Будущая реализация должна обрабатывать повреждённый JSON, неизвестную версию и ошибки записи без молчаливого уничтожения данных. Игровая логика и отображение не должны зависеть напрямую от `localStorage`. Это позволит позже добавить отдельный адаптер синхронизации без переписывания расчётов; сама синхронизация пока не создаётся.

## Границы модулей

- `time`: время сервера, игровые дни, недели и моменты сброса. Часовой пояс устройства не должен незаметно менять игровой период.
- `src/core/resin.js`: чистые расчёты восстановления и расхода по снимку и переданному времени. `modules/resin/resinTracker.js` добавляет записи в состояние; `modules/rendering/resinWidget.js` отображает карточку и обрабатывает формы.
- `storage`: единый документ, версии, проверка данных и операции сохранения.
- `rendering`: DOM, навигация между семью экранами и обработка действий пользователя.
- `main.js`: соединение модулей после их реализации.

Расчёты времени и смолы должны получать исходные данные и текущее время аргументами. Это позволяет воспроизводить результат и тестировать границы сбросов и восстановления.

## Проверки будущих этапов

Игровую логику сопровождать тестами `node --test`: до, в момент и после сброса; восстановление смолы и её пределы; повторные отметки выполнения в одном периоде. Хранилище проверять на сохранение и восстановление данных, несовместимые версии и ошибки. Для экранов отдельно проверять основные действия в браузере.

## Готовность текущего этапа

Готова адаптивная оболочка с семью разделами, двумя темами и пятью обзорными карточками. Визуальные элементы созданы локально средствами CSS и SVG, без игровых изображений, сторонних шрифтов и сетевых зависимостей. Старая страница сохранена отдельно как `legacy-birthday.html`.

Единый модуль `src/modules/storage/storage.js` читает, валидирует и записывает документ версии 1. При ошибке приложение сообщает о ней и работает с временными настройками в памяти, сохраняя исходный документ. Сохраняются тема, последний раздел, локальный профиль, шаблоны рутины, история отметок и записи замеров/расхода смолы.

Тесты хранилища запускаются командой `npm test`. Навигация, темы, перезагрузка и адаптация проверены в Chromium. Внешний каталог персонажей не подключается: карточки, материалы и расписания вводятся вручную. Личные задачи и статистика реализованы без внешних сервисов и дублирующих счётчиков. Восстановление и расход смолы покрыты автоматическими тестами; карточка проверена в браузере.


## Реализованный контракт рутины

- `profiles`: для текущего локального профиля добавлены `server` (`europe`, `america`, `asia`) и `routineSeeded` (однократная инициализация примеров). `settings.activeProfileId` указывает текущий профиль. Новые поля необязательны при чтении прежней пустой основы версии 1; существующие коллекции и история не очищаются.
- `taskTemplates`: `id`, `profileId`, `title` (1–100 символов без окружающих пробелов), `period` (`daily`/`weekly`), `target` (целое 1–999), `enabled` (boolean).
- `completions`: `id`, `profileId`, `templateId`, `periodKey`, снимки `title` и `target`, целое `count` от 0 до `target`, UTC-метки `createdAt` и `updatedAt`. Комбинация профиля, шаблона и периода уникальна. Ссылка на удалённый шаблон допустима: снимок истории самодостаточен.
- `periodKey`: `${serverId}:${type}:${startDate}`, например `asia:weekly:2026-10-19`. Дата — день начала игрового периода на сервере, а не дата компьютера. Для недельных ключей проверяется понедельник.
- Все вычисления времени выполняются в `src/modules/time/gameClock.js`, принимают время аргументом и используют UTC-методы. Europe UTC+1, America UTC−5, Asia UTC+8; без DST. День начинается в 04:00; неделя — в понедельник в 04:00.
- Одна операция `+` добавляет одну отметку, `−` отменяет её только в текущем периоде. Отключение запрещает новые отметки, но допускает отмену. Изменение шаблона не переписывает снимки уже начатых периодов, включая текущий. Удаление шаблона не удаляет `completions`.
- Сброс не является изменением данных: расчёт выбирает другой ключ. До первой отметки счётчик равен нулю, но запись истории не создаётся. Чтение, таймер и переход через сброс не меняют прежние записи автоматически.
- Кнопки счётчика передают отображённый ключ периода. Если момент сброса наступил до нажатия, устаревшее действие отклоняется с предложением повторить его в новом периоде.
- Таймер обновляет отображение каждую секунду и при возвращении на вкладку. Переход через сброс сохраняет незавершённый ввод в форме; при уходе из раздела таймер и его обработчики удаляются.
- Четыре стартовых примера редактируются, отключаются и удаляются как обычные шаблоны. Примеры не возвращаются после удаления. Сервер по умолчанию Europe, выбор доступен в «Рутине» и сохраняется в профиле.
- При ошибке хранения изменения остаются в памяти текущей вкладки, включая переключение страниц и темы. Ошибка видна пользователю; успешное сохранение не заявляется. Другие сервисы и синхронизация не подключены.


## Реализованный контракт Первородной смолы

- Расчёты находятся строго в `src/core/resin.js`. `createResinSnapshot(amount, now)`, `calculateResin(snapshot, now)` и `spendResin(snapshot, cost, now)` — чистые функции без доступа к хранилищу и системным часам. `now` — корректный `Date` либо целые миллисекунды Unix.
- Ручной замер: целое `amount` от 0 до 200; `measuredAt` — каноническая ISO-строка UTC с суффиксом `Z`; `progressMs: 0`. Количество без замера не предполагается: интерфейс показывает пустое состояние.
- Проекция: `min(200, amount + floor((now − measuredAt + progressMs) / 480000))`. Время до заполнения учитывает неполный интервал. На лимите остаток интервала равен нулю, лишнее время не запасается.
- Расход: целый `cost` от 1 до 200, не больше рассчитанного количества на момент действия. Новый снимок содержит расчётный остаток после расхода, UTC-время действия и незавершённую часть восьмиминутного интервала в `progressMs`. Ручная коррекция обнуляет эту часть.
- В `resinSnapshots` сохраняются `id`, `profileId`, `source` (`manual`/`spend`), `amount`, `measuredAt`, `progressMs`; для `spend` также `spent`. Все записи проходят проверку в `storage.js`. Текущий снимок — последняя добавленная запись активного профиля, а не максимальная дата: это позволяет исправить замер после отката часов. Данные других профилей не смешиваются.
- Новые замеры и расходы добавляются в массив без изменения предыдущих. Чтение, таймер и перезагрузка не создают новых снимков и не начисляют восстановление повторно. Первое сохранение при отсутствии профиля создаёт локальный профиль без демонстрационных шаблонов рутины.
- На «Обзоре» доступны количество, шкала 0–200, время до заполнения, приблизительная дата заполнения по времени устройства, ручная коррекция и расход 20/40/60 либо произвольная сумма. Поля формы не теряются при автообновлении. Таймер обновляется каждую секунду и при возвращении к вкладке, удаляется при уходе со страницы.
- Замер из будущего не приводит к отрицательному восстановлению: показывается исходное количество и предупреждение, расход временно запрещён, ETA скрывается до коррекции времени/замера.
- Предупреждение в карточке объясняет приблизительность и отсутствие чтения аккаунта HoYoverse. При ошибке сохранения данные остаются в памяти вкладки, обратная связь явно сообщает об отсутствии успешного сохранения.


## Реализованный контракт персонажей и фарма

- `characters`: `id`, `profileId`, `name` (непустая строка до 100 символов), `notes` (до 2000 символов), `targetLevel` (положительное безопасное целое; игровой предел не выдумывается). Данные пользователя экранируются при отображении.
- `materialGoals`: `id`, `profileId`, `characterId`, `name`, целые `owned` и `needed` от 0 до 1 000 000 000, `days` — уникальные целые 1–7. Пустое расписание допустимо, без предположений о ежедневной доступности. Запас относится к цели конкретного персонажа.
- `farmPlans`: `id`, `profileId`, `materialGoalId`, `title` (1–100 символов), `notes` (до 2000 символов), непустой набор `days` и `completedAt` (null либо каноническая ISO-строка UTC). Персонаж определяется через материал. Расписание плана независимо от расписания доступности материала и вводится вручную.
- Прогресс: `floor(100 * sum(min(owned, needed)) / sum(needed))`. Пустой набор = 0%; непустой набор с нулевой общей потребностью = 100%, без деления на ноль. Дефицит строки = `max(0, needed - owned)`. Процент не означает расчёт фактического уровня персонажа.
- Общий список дефицита группируется по вручную введённому названию (без учёта регистра и внешних пробелов), сохраняя привязку к персонажам. Итоги учитывают текущий фильтр дней. Запасы разных персонажей не объединяются и не распределяются автоматически.
- Фильтры `today`, `tomorrow`, `week`: серверный игровой день определяется через `gameClock.js`, с границей 04:00 и нумерацией понедельник = 1, воскресенье = 7. Завтра после воскресенья — понедельник. Во всей неделе видны и материалы с неизвестными днями. Планы фильтруются по собственным дням. `settings.farmFilter` сохраняет выбор.
- Выполнение и отмена плана меняют только `completedAt`, не инвентарь и не прогресс. Изменение плана сохраняет отметку выполнения. Отметки не сбрасываются автоматически по неделям.
- Удаление персонажа каскадно удаляет его `materialGoals` и связанные `farmPlans`; удаление материала — связанные планы. UI требует подтверждения и объясняет последствия. Другие персонажи и их данные не затрагиваются.
- `storage.js` проверяет поля и связи в рамках одного профиля. Чистые операции и вычисления находятся в `src/core/charactersFarm.js`, интерфейс — в `plannerPage.js`, сводка главной — в `plannerViews.js`. Версия документа остаётся 1, прежние пустые коллекции совместимы.
- При ошибке записи действует общий режим временных данных в памяти вкладки с явным предупреждением. Новые внешние сервисы, игровые базы и предполагаемые расписания не добавлены.


## Реализованный контракт личных задач и статистики

- `personalTasks`: `id`, `profileId`, `title` (1–100 символов), `category` (1–50, без окружающих пробелов, пользовательский ввод нормализуется в нижний регистр), `priority` (`low`/`normal`/`high`), `status` (`planned`/`in-progress`/`completed`), `dueDate` (null либо реальная дата YYYY-MM-DD), `notes` (до 2000), UTC-поля `createdAt`, `updatedAt`, `completedAt`.
- `completedAt` — null для незавершённых задач и каноническая UTC-строка для выполненных. Редактирование выполненной задачи не переносит время выполнения. Возврат в работу или запланированный статус очищает отметку; повторное выполнение получает новое время. Удаление удаляет и задачу, и её вклад в текущие итоги.
- Категории по умолчанию: квесты, исследование, достижения, прокачка, другое. Свои категории сохраняются в необязательном `profiles.personalCategories`; предлагаются повторно даже после удаления задач. Новая коллекция не требуется. `settings.goalFilters` хранит совместные фильтры: status/priority с `all`, category с null для «все» либо строкой категории.
- Чистые операции задач находятся в `src/core/personalTasks.js`; `nearestGoals` возвращает незавершённые задачи, сначала с ближайшим сроком. Срок — дата без часового пояса и автоматических переходов статуса.
- Для новых отметок рутины добавлено необязательное `completions.actionTimes`: массив UTC-времён сохранённых единичных действий, длина не больше `count`. Новая отметка добавляет время, отмена удаляет последнюю датированную отметку. В старом счётчике может оставаться `count - actionTimes.length` недатированных действий. Их время не восстанавливается автоматически. Записи прошлых периодов при просмотре не меняются.
- `calculateStatistics(state, now)` в `src/core/statistics.js` не изменяет состояние и не сохраняет результаты. Итоги 7/30 дней — последние 7/30 игровых дней текущего сервера, включая сегодняшний, с отсечением будущих времён. Действия состоят из датированных отметок рутины, текущих completedAt личных задач и выполненных планов фарма активного профиля.
- Недатированные старые действия показываются отдельно и не включаются в точные дневные столбцы или итоги 7/30. Текущий прогресс рутины при этом использует сохранённый count и снимки целей; удалённые/отключённые шаблоны с отметками не пропадают из текущего прогресса.
- Завершённые личные задачи считаются за всё время среди текущих сохранённых задач. Материалы используют ту же функцию прогресса, что «Персонажи» и «Обзор», включая безопасную нулевую потребность.
- Дневные данные содержат число датированных действий и признак наличия записи. Пустой день отображается как «нет записей», а не «пропуск». Нулевая датированная активность при существующей записи отличается от отсутствия данных. Журнал повторных выполнений личных задач и серии пропусков не создаются.
- UI статистики использует CSS-столбцы, полосы progress и таблицу значений без библиотек. При изменении состояния пересчитывается по событию `teyvat:change`, при переходах между разделами — заново; при смене игрового дня обновляет окно. Таймеры и обработчики удаляются при уходе со страницы.
- Версия JSON остаётся 1; старые записи рутины без actionTimes читаются и сохраняются. Все новые поля проходят проверку storage. Ошибки хранения обрабатываются общим режимом памяти вкладки, без ложного сообщения о сохранении.


## MVP 1.0: настройки и безопасный перенос данных

Версия приложения 1.0.0 использует прежнюю JSON-схему 1. Все семь разделов доступны; публикация остаётся отдельным действием владельца.

- Сервер выбирается в «Настройках» и «Рутине», применяется к текущему профилю и не удаляет историю других серверов. Смена темы сохраняется в settings.
- Экспорт сериализует весь рабочий документ со всеми профилями, коллекциями и безопасными дополнительными полями. Отдельная локальная резервная копия не вкладывается в рабочий экспорт: она скачивается своей кнопкой.
- Импорт принимает JSON схемы 1 до 5 МиБ. Помимо предметных полей проверяются конечные JSON-значения, отсутствие опасных ключей объектов, глубина до 32 и ограничение обхода, формат ID (1–128 символов: буквы/цифры с допустимыми точками, подчёркиваниями, дефисами и двоеточиями; начало — буква или цифра), уникальность внутри коллекции и ссылки одного профиля.
- Снимок завершения может ссылаться на удалённый шаблон: это разрешённая история. Если шаблон существует, ссылка на чужой профиль не допускается. Пользовательские текстовые поля отображаются через экранирование или textContent, а не как разметка.
- После выбора файла создаётся только проверенный предпросмотр количества записей. Обязательны флажок и отдельная кнопка подтверждения. Изменение состояния после предпросмотра требует нового предпросмотра; незавершённые чтения файла отменяются при уходе или начале очистки.
- Резервная копия записывается до замены в вспомогательный `teyvat-tasks:backup:v1`: UTC createdAt, причина before-import/before-delete, data текущей вкладки и, при отличии, previousStoredRaw. Рабочая база по-прежнему одна — `teyvat-tasks:v1`.
- Ошибка создания копии запрещает замену/очистку. Ошибка новой записи сохраняет старый рабочий ключ и уже записанную копию. Отдельные setItem атомарны для ключа; общей транзакции/слияния между вкладками нет. Проверяется актуальность исходного текста перед копией и ещё раз перед заменой.
- Явное восстановление может заменить повреждённую рабочую запись, сохранив её исходный текст в копии. Автоматические обычные записи по-прежнему не перезаписывают повреждённый документ. Обычная запись с обнаруженным устаревшим текстом другой вкладки блокируется.
- Удаление рабочих данных требует отдельного подтверждения, предварительно создаёт копию и восстанавливает начальное состояние. Копия намеренно сохраняется; для удаления и её пользователь очищает данные сайта браузером.
- GitHub Pages подготовлен только для ручного workflow_dispatch. Перед публикацией запускается npm test, затем готовится _site из index.html, src и .nojekyll. Старые страница и видео сохраняются в репозитории, но не включаются в артефакт. Ни удалённый workflow, ни git push на этапе проверки не запускались.

Результаты и ограничения выпуска: [MVP-1.0-REPORT.md](MVP-1.0-REPORT.md).
